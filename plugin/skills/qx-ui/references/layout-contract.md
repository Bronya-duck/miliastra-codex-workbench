# 布局交付约定

所有表格和树使用同一套稳定设计 ID。设计 ID/名称由方案定义；官方控件类型与属性名称按本机知识库核实；编辑器实际控件 ID、布局索引、模板索引填实测值，未知时标“待填写”。

## 布局基准

说明目标设备、画布/参考分辨率、宽高比、安全区域、坐标单位、原点、正方向、中心/枢轴、锚点与缩放规则。用户未给尺寸时先给明确的建议基准并标假设；继续完成方案，不把缺少尺寸当作停止原因。不同设备有差异时列覆盖值。

区别编辑器坐标、Lua 父级相对位置和示意图屏幕坐标。表格中的位置须标明相对谁；若给屏幕矩形，还需说明转换和适用条件。拉伸锚点、非默认枢轴、父级缩放/旋转会影响结果，不能只相加偏移。给出窄屏、宽屏和移动端适配检查。

传统布局查《界面布局》`mhozt0r74ng6`、《界面控件》`mhnapxrumtzy`；客户端查《客户端控件容器》`mhlz2lrly3dq`、《客户端控件和客户端脚本》`mhbgxf0nynww`、《客户端控件API》`mhtakr07vej4`，再查本次实际使用的控件全文。文档 ID 用于定位，结论使用工具返回的活动资料版本。

## 完整控件树

用文本树覆盖所有页面、宿主、容器和叶控件，区分页面关系与实际编辑器父子关系。标记控件类型、设计 ID、父级、端/控制方式，以及新增、已有复用或后续预留。相关固有 HUD 按官方分类核对，作为避让约束；场景未提供时标存在状态和位置待现场确认，不能把候选控件写成已存在。预制计时器等业务控件与固有 HUD 分开；不凭空改变固有控件。

客户端方案列出界面布局中的客户端控件容器，以及其中的根控件和子控件。只有实际支持的类型才用作可创建控件；“HUD 层”“弹窗层”等概念分组若无对应控件，标为逻辑分组。模板引用与运行时实例区分，动态生成前核对模板根节点限制。

## 谁依赖谁

树表示父子结构，另给依赖表：

| 对象 ID | 依赖对象/数据 | 依赖类型 | 触发或更新时机 | 隐藏/销毁/失败时处理 |
|---|---|---|---|---|

涵盖父级变换与裁剪、激活和生命周期、可见性、数据来源、事件/信号、脚本宿主、资源/模板、手柄导航。区分本地展示状态与服务端权威状态。写清数据 → 显示，以及点击 → 处理 → 更新的路径；使用 `qx-build` 已定变量和信号。跨端必须查官方通信能力，不能用本地 Lua 状态冒充多人共享结果。

## 每个控件的配置

先给位置和层次总表，再逐控件补齐类型专有属性。控件多时可按页面分表，但每个树节点都应有配置或明确的逻辑分组/只读说明。

| 设计 ID / 编辑器名称 | 官方类型与控制端 | 父级 / 查找路径 | 位置 x,y 与基准 | 宽高 / 缩放 / 旋转 | 锚点 / 中心 | 显示顺序 | 初始激活 / 可见 / 交互 |
|---|---|---|---|---|---|---|---|

按适用类型填写：文本内容/绑定、字体字号/对齐/颜色、图标或图片资源、按钮各状态、音效、裁剪/遮罩、透明度、点击区域/射线、事件穿透、手柄四向导航、脚本文件/映射/挂载点、模板和布局引用。每项明确给值、沿用已核实默认值、不适用或待确认；“默认”须有资料依据或现场证据。共用样式可定义一次并明确引用，差异逐项列出。

把编辑器属性名、Lua 字段/方法、方案中的业务变量分开。按官方 API 核对可写性，不对只读字段赋值；控件不支持的属性填“不适用”。涉及状态变化时补初始、正常、按下、禁用、弹窗打开/关闭的值与更新来源。设计建议和官方能力用不同来源标记。

## 画面深浅与遮挡

“深浅”默认解释为前后显示顺序，同时独立列颜色与透明度。输出从后向前的顺序和重叠关系，并说明弹窗/遮罩是否挡住或放行点击。

核对传统控件的时序渲染/层级渲染模式、层级数值和同层级创建顺序；客户端核对父级及同级顺序。布局内控件、激活模板、客户端宿主和不同父级可能有不同排序范围，分别列出。不能用一个虚构的通用 `zIndex` 排所有控件，也不能用透明度解决点击穿透。对无法凭资料确定的跨容器遮挡给最小重叠测试；不要承诺未验证的全局优先级。

旧场景模式未知时标待核对，并提供沿用当前模式的步骤；切换模式属于编辑器改动，须按用户授权执行。遮罩、背景、正文、操作按钮、提示和弹窗各自排序及输入优先级都要能追溯到实际配置。

## 配置顺序、验收与复用

按布局/宿主 → 父容器 → 子控件 → 样式与变换 → 数据/事件绑定 → 层级与输入 → 试玩给出操作步骤和人工填写项。给出简洁线框或区域示意时说明它使用的坐标，保证与配置表一致；示意图不算编辑器完成证据。

验收至少覆盖本段需要的分辨率适配、HUD 遮挡、重叠显示/点击、关闭重开、父级隐藏/销毁、数据刷新和相应设备输入。未试玩明确标待验证。布局表校对通过不能代表关卡交互已通过。

已启用项目保存到 `.miliastra/layouts/<阶段ID>/layout-r<下一revision>-<唯一后缀>.md`，保留旧版，用唯一后缀避免并行聊天互相覆盖文件。数据库 `artifacts` 登记路径和相关脚本/资源，`sources` 登记文档 ID、官方链接、快照与已读图片 ID。保存的正文含本约定全部结果、对应阶段、设计假设和验证边界，让后续 `qx-build` / `qx-lua` 直接复用。数据库写法读取 `../../qx-plan/references/database.md`；先读最新 revision，提交时合并旧产物。实际提交版本以数据库返回为准，冲突时重新读取合并，不覆盖其它聊天的产物。

如果无项目库，通常聊天交付；用户要求启用时交由 `qx-plan` 初始化和绑定，要求保存时按指定位置保存。无阶段的独立布局请求可由 `qx-plan` 按该需求新增布局阶段，保留原计划；不要冒充已存在的阶段。修改已验证布局或绑定逻辑时填写 `changes_made:true`，使受影响阶段重新待验证；纯补充资料保留已有状态。
